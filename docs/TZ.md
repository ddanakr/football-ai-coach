# Football AI Coach (P01) — Техническое задание

Nov 2, 2026 · @Alfaworker

## 1. Контекст и цель

Football AI Coach превращает запись матча КПЛ в каталог событий с точными таймкодами и отвечает на вопросы по матчу. Это проект P01 программы KOZ AI: срок 2 недели, исполнитель один, работа идёт в связке с Claude Code.

**Бизнес-проблема.** Аналитики и тренеры вручную ищут эпизоды (гол, удар, угловой, фол, замена) в полных записях матчей. Время ручного поиска пока гипотеза: она проверяется в разделе 5.

**Что делаем.** Пользователь вставляет ссылку на YouTube-трансляцию KFF LEAGUE. Система строит таймлайн из 5 категорий, аналитик исправляет метки и экспортирует клипы, а агент отвечает на вопросы по событиям, игрокам и эпизодам со ссылками на таймкоды.

**Ключевая идея.** Гибридный подход:

- плашки и табло трансляции почти детерминированно дают замены, голы и карточки;
- обученная модель SoccerNet нужна для ударов, угловых и фолов;
- время событий дают компьютерное зрение и OCR, а смысл (кто, как, что сказали) добавляет языковая модель.

**Как оценивают.** Куратор смотрит на баланс технического качества и бизнес-ценности: кому полезно и можно ли применить на практике. На защите показываем работающий прототип, источники и измеримые результаты.

## 2. Пользователи и сценарии

Основной пользователь — аналитик клуба, который после матча готовит разбор для тренера. Тренер вторичен: он получает результат (клипы, нарезки), а таймлайном и правками занимается аналитик. Скаут вне MVP, потому что ему нужны данные по конкретному игроку (кто бил, кто выиграл единоборство), а трекинга игроков у нас нет.

| Сценарий | Кто | Что делает система |
| --- | --- | --- |
| Нарезка стандартов | аналитик → тренер | все угловые тайма одним списком, экспорт клипов |
| Моменты у ворот | аналитик | удары и голы с переходом к эпизоду |
| Разбор замен | аналитик | кто вышел, кто ушёл, команда, момент появления плашки |
| Вопрос к агенту | аналитик | «что было с игроком на 60-й», «как забили гол» — ответ со ссылками на таймкоды |

**Рабочая точка.** Для аналитика важнее Recall, чем Precision: лишнюю метку удалить за секунду, а пропущенный гол или замена подрывают доверие ко всему инструменту. Порог выбирается с упором на Recall, а «число правок на матч» входит в главные метрики.

## 3. Объём MVP

MVP работает на одном матче KFF LEAGUE и 5 категориях событий; всё остальное сознательно вынесено за рамки.

**Входит:**

- 5 категорий: гол, удар, угловой, фол, замена;
- плашки и табло трансляции как главный источник для замен, голов и карточек;
- команда события по логотипу на плашке (замены, карточки, голы);
- русский и казахский языки в речи комментаторов, в вопросах и ответах агента;
- исправление меток, экспорт клипа, оценка качества на размеченном тайме.

**Не входит:**

- распознавание и трекинг игроков, передачи, xG, тактика, владение мячом;
- определение команды по цвету формы (Roboflow): для ударов, угловых и фолов команда может быть неизвестна, тогда `team = null`, и агент об этом говорит;
- дообучение сквозных видеомоделей и обучение с нуля;
- скаутские сценарии, статистика по игроку сверх того, что показано на плашках и сказано в комментарии;
- авторизация, многопользовательский режим, развёртывание в production.

## 4. Функциональные требования

Минимальный рабочий набор покрывает 6 пунктов задания; приоритет MUST означает «без этого демо не принимается».

| ID | Требование | Приоритет |
| --- | --- | --- |
| FR-1 | Пользователь вставляет ссылку на YouTube-трансляцию и запускает обработку | MUST |
| FR-2 | Система показывает стадии обработки (загрузка, признаки, плашки, речь, объединение) и не теряет прогресс при обрыве | MUST |
| FR-3 | Таймлайн содержит 5 категорий; для каждого события хранится время в секундах видео, тайм, игровая минута, команда (если известна), уверенность и источники | MUST |
| FR-4 | Для каждого события есть ссылка на исходный фрагмент (YouTube с параметром времени) | MUST |
| FR-5 | Список событий фильтруется по категории; клик переводит встроенный плеер на момент события | MUST |
| FR-6 | Метку можно сдвинуть, сменить категорию, удалить, добавить в текущий момент плеера; правки сохраняются отдельным журналом, исходные предсказания не изменяются | MUST |
| FR-7 | Экспорт клипа через FFmpeg: по умолчанию 8 с до и 12 с после события, значения настраиваются; клипы хранятся только локально | MUST |
| FR-8 | Агент отвечает на вопросы трёх типов (события, игрок, эпизод) на русском и казахском со ссылками на таймкоды | MUST |
| FR-9 | Экспорт проверенных и исправленных меток в JSON эталона для оценки | SHOULD |
| FR-10 | Нарезка всех событий выбранной категории одним клипом | SHOULD |
| FR-11 | Описание эпизода по кадрам через vision-модель с пометкой «по кадрам, не проверено» | SHOULD |

## 5. Метрики и методика оценки

Главная метрика — доля найденных событий в допуске ±5 и ±10 с при заданной точности: аналитик получает клип с запасом, поэтому ему важнее найти эпизод, чем попасть в секунду. Строгие метрики идут дополнением.

| Метрика | Что показывает | Как считаем |
| --- | --- | --- |
| Recall@±5 с, ±10 с | доля эталонных событий, найденных системой | жадное сопоставление предсказания с ближайшим свободным эталоном того же класса |
| Precision@±5 с, ±10 с | доля верных предсказаний в рабочей точке | то же сопоставление, порог выбран с упором на Recall |
| Ошибка таймкода | на сколько секунд система ошибается | медиана и 90-й процентиль по найденным событиям, по классам |
| mAP при допусках | качество ранжирования по всем порогам | AP по классам, среднее по сеткам допусков 1–5 с (строгая) и 5–30 с (мягкая); дополнение |
| Правок на матч | сколько кликов нужно, чтобы довести таймлайн до 100% | число операций в журнале правок за сеанс |
| Время поиска | экономия времени аналитика | эксперимент в разделе ниже |
| Стоимость матча | себестоимость обработки | GPU-время плюс токены API (раздел 10) |

**Протокол.** Подбор порогов и окон идёт на 1-м тайме, итоговые цифры считаются на 2-м. Для малого числа событий дополнительно приводятся доверительные интервалы (bootstrap по событиям). В коде оценки допуск ±δ записывается так, как в SoccerNet: там δ — ширина окна, то есть ±δ/2; в отчёте это указано явно.

**Ablation.** Строка за строкой показываем, что даёт каждый компонент: только CV, затем плашки и табло, затем подавление повторов, затем речь, затем стекер против правил. Если стекер не побеждает простые правила на 2-м тайме, в итоговую систему он не входит.

**Сравнение с Gemini.** Видео-LLM в YouTube получает тот же тайм и один заранее записанный запрос с просьбой выдать события с таймкодами; те же метрики считаются для её ответов. Вывод ограничен тем, что такой запуск нельзя повторить пакетно.

**Эксперимент по экономии времени.** Два человека, у каждого один тайм вручную и второй с системой (порядок меняется). Категории: угловые, замены и одна субъективная (фол или удар); определения событий выданы письменно. Фиксируется время и итоговые Precision и Recall списка в обоих режимах, потому что человек, проверяющий готовый список, склонен не замечать пропусков. Выборка из двух человек — пилот, и в отчёте так и называется. Цифры «40–50 минут вручную против 5 с системой» остаются гипотезой, результатом считается только измеренное.

Целевые значения метрик фиксируются после первого прогона на 1-м тайме (конец недели 1), а не заранее.

## 6. ML-пайплайн

Только три категории (удар, угловой, фол без карточки) требуют обученной модели; замены, голы и карточки закрывает разбор графики эфира, а речь служит подсказкой и источником смысла для агента.

| Категория | Главный источник | Страховка |
| --- | --- | --- |
| Замена | плашка замены (логотип, номера, фамилии, стрелки) | слова комментатора, модель SoccerNet |
| Гол | смена счёта на табло и плашка «ГОЛ» | модель SoccerNet, всплеск громкости |
| Фол | модель SoccerNet и свисток; плашка карточки как сильный усилитель | слова комментатора |
| Удар | модель SoccerNet | слова комментатора, подавление повторов |
| Угловой | модель SoccerNet | слова комментатора |

**Три шкалы времени.** Первичный ключ — время видео `t_v` в секундах: по нему работают плеер и FFmpeg. Вторичные — тайм и игровая минута; соответствие `t_v` → минута строится по OCR табло.

**1. Загрузка.** `yt-dlp` скачивает видео до 720p и аудио отдельно; из аудио получается моно 16 кГц для распознавания речи. Скачивание допустимо только для разрешённых трансляций и только локально.

**2. Табло и плашки.** Табло обнаруживается в фиксированной области кадра; счёт и часы читаются раз в секунду с медианным фильтром и проверкой монотонности. Плашки замены, карточки и гола находятся по форме и цвету (стрелки, цвет карточки, логотип), а текст читается OCR с казахским языком или vision-моделью по вырезанному кадру: таких кадров десятки за матч. Табло исчезает не только на повторах, но и на крупных планах в живой игре и на части плашек (на плашках карточек и голов его чаще всего нет). Видимость табло это признак, а не повтор; повторы определяем отдельным детектором, признаки для него уточняются по кадрам.

**3. Время гола.** Плашка гола выходит позже удара, поэтому она подтверждает гол и сообщает минуту, но не секунду. Окно поиска: от начала указанной минуты до появления плашки плюс запас 10–15 с; внутри окна момент берётся по пику оценки CV и всплеску громкости. Нужно отдельно разобрать добавочное время («45+2'») и сдвиг минуты на табло. Если счёт вырос, а потом вернулся (VAR), событие получает `status = disallowed` и в метриках считается ударом.

**4. Признаки и модель.** Две ветки, выбор к концу 4-го дня по мягкой метрике на 1-м тайме:

- **Ветка A (базовая):** признаки ResNet-152 на 2 fps с PCA до 512 (экстрактор SoccerNet DevKit, TensorFlow) → NetVLAD++, обучение на готовых признаках `SN-Features` и применение к KFF;
- **Ветка B (если найдётся чекпоинт SoccerNet):** T-DEED по кадрам, без обучения; лицензия GPL-3.0, размер кадра в инференсе должен совпадать с обучением.

Ожидаем, что ResNet-версия находит «примерно где», но не точную секунду; для продукта это допустимо, поскольку клип экспортируется с запасом. Признаки Baidu для KFF не берём: их экстрактор тяжёлый и рассчитан на кластер.

**5. Пики.** Для каждого класса применяется NMS со своим окном (стартовые значения: гол 20 с, удар 6 с, угловой 10 с, фол 6 с, замена 20 с; подбираются на 1-м тайме). Для mAP порог низкий, для пользователя рабочий порог выбирается отдельно с упором на Recall.

**6. Речь.** Аудио режется по паузам (VAD) на короткие реплики; для каждой язык выбирается только из русского и казахского; далее `faster-whisper large-v3` с метками времени слов. Фамилии с плашек подаются как подсказка (проверяется на выборке: возможны галлюцинации). Перекрывающуюся речь комментаторов теряем, это указано в ограничениях. Качество казахского проверяется на 5 минутах комментария до того, как на него опирается лексикон.

**7. Лексикон.** Русский список (начальные формы через pymorphy3) и казахский список, который составляет и проверяет автор. В каждом списке есть стоп-фразы («повтор», «отменён», «офсайд»). Комментатор называет событие с задержкой, поэтому улика сворачивается с ядром по классу: задержки оцениваются на разметке. Список дополняется словами, которые чаще встречаются рядом с эталонными событиями.

**8. Объединение.** Основной режим — правила: плашка или смена счёта подтверждает событие, слово из лексикона и всплеск громкости повышают уверенность, повтор понижает, повторные срабатывания подавляются в пользу оригинала. Рядом обучается мини-стекер: одна общая логистическая регрессия на 4–6 признаков (уверенность CV, наличие слова, громкость, повтор, класс), обучение на 1-м тайме, проверка на 2-м. Стекер входит в итог, только если превзошёл правила.

## 7. Агент AI-аналитик

Агент — языковая модель с инструментами над таблицами событий и транскриптом, а не «весь матч в контекст»; все числа и таймкоды она получает из инструментов и сама их не пишет.

**Типы вопросов (охват MVP):**

- по событиям: «сколько угловых во втором тайме», «покажи все удары»;
- по игроку: «что было с игроком на 60-й минуте» — эпизоды, где он упомянут, заменён или получил карточку, и пересказ по комментарию;
- по эпизоду: «как забили гол» — описание по кадрам и комментарию.

Вне охвата: тактика, статистика игрока (пасы, пробежки), владение мячом.

| Инструмент | Что возвращает |
| --- | --- |
| `query_events` | события по фильтрам (категория, тайм, интервал минут, команда, уверенность, статус) и их число; считает код, а не модель |
| `get_event` | событие с соседями по времени и фрагментом транскрипта |
| `get_transcript` | реплики за интервал времени с идентификаторами |
| `search_transcript` | поиск по репликам: BM25 плюс многоязычные эмбеддинги в памяти |
| `find_player` | игрок по фамилии из словаря плашек и его события |
| `get_frames` | 4–6 кадров вокруг момента для vision-модели |
| `make_clip` | клип по списку событий |

**Защита от выдумок.**

1. Ответ приходит структурой: текст плюс список утверждений, у каждого идентификаторы событий или реплик как доказательства.
2. Проверяющий код сверяет, что идентификаторы существуют и числа в тексте совпадают с результатами инструментов; при расхождении ответ перегенерируется или помечается.
3. Кликабельные таймкоды подставляет интерфейс по идентификаторам: модель не может написать время сама.
4. События со `status = auto` и низкой уверенностью подаются с пометкой, и ответ обязан об этом сказать. Если данных нет, ответ «в данных нет».
5. Описание по кадрам помечается «по кадрам, не проверено» и считается уликой, а не фактом.

**Игроки.** Словарь строится автоматически из плашек замен, карточек и голов (номер, фамилия, команда). Игроки, которых ни разу не показали, в словаре отсутствуют: это ограничение. Чтобы фамилия с плашки совпадала с речью и вопросом, применяется нормализация (Ә→А, Ө→О, Ү и Ұ→У, Қ→К, Ғ→Г, Ң→Н, Һ→Х, І→И) и нечёткое сравнение по основе; для казахского вместо лемматизации используются символьные n-граммы.

**Казахский язык.** Ответ даётся на языке вопроса. Метки данных нейтральны (`corner`, `subst`), названия в интерфейсе и ответах есть на русском и казахском. Казахские формулировки и список слов проверяет автор. В тест входят несколько вопросов на казахском. Для эмбеддингов берётся локальная многоязычная модель (семейство bge-m3 или multilingual-e5); пригодность для казахского проверяется на выборке.

**Модели и стоимость.** Языковая и vision-модели вызываются через API; разработка идёт на дешёвой модели, финальная оценка и запись демо на более сильной. Whisper, OCR и эмбеддинги работают локально.

**Оценка агента.** 20–30 вопросов трёх типов. По событиям ответы проверяются автоматически по эталону, по игроку и эпизоду вручную по критерию «утверждение подтверждено источником»; доля ответов с проваленной проверкой ссылок считается отдельно.

## 8. Данные и разметка

Используются только собственные, открытые или разрешённые материалы: 1–2 трансляции KFF LEAGUE и открытые части SoccerNet.

**Источники.**

- **KFF LEAGUE.** Список разрешённых стримов и право скачивать их локально для разработки уточняются у куратора. В репозиторий попадают код, ссылки на видео, таймкоды и разметка; видео, клипы и кадры добавляются в `.gitignore`.
- **SoccerNet.** Признаки (ResNet на 2 fps, в том числе с PCA до 512) и разметка событий открыты на HuggingFace. Видео SoccerNet закрыто (запрос доступа, условия или NDA) и для MVP не нужно: ветка A учится на готовых признаках. Условия лицензии указываются в отчёте одной строкой.

**Протокол разметки.** Определения фиксируются письменно до начала разметки, их же получают участники эксперимента по времени.

| Категория | Что считается моментом события |
| --- | --- |
| goal | мяч пересёк линию ворот; отменённый гол размечается как shot со статусом disallowed |
| shot | момент удара |
| corner | момент подачи |
| foul | момент контакта |
| subst | момент появления плашки замены; расхождение с реальным выходом игрока измеряется на выборке и указывается в отчёте |

Для каждого события записываются `t_v` (секунды видео), тайм, минута, команда (если видна), признак повтора и видимость (показано в эфире или нет). Соотношение классов goal и shot фиксируется на первых 10 минутах разметки и записывается в `CLAUDE.md`.

**Эталон.** 2-й тайм размечается с нуля, не глядя на предсказания модели: иначе разметчик подсознательно подтверждает их и метрики завышаются. Порядок величины для тайма — несколько десятков отметок. 1-й тайм служит для подбора порогов и окон и может размечаться исправлением предсказаний; исходные предсказания сохраняются отдельно. Если куратор даст второй матч, он становится независимым тестом.

**Задержки плашек.** При разметке для каждого гола, карточки и замены записывается разница между событием и появлением плашки: из неё получаются окна поиска и ядра задержки речи.

**Формат.** JSON с массивом событий; поля: `type`, `t_v`, `half`, `clock`, `team`, `visibility`, `replay`, `annotator`.

## 9. Архитектура и инфраструктура

Обработка матча идёт офлайн отдельными стадиями-командами, а интерфейс и агент читают одну общую базу SQLite.

&#91;embedded content: архитектура MVP · 3 параллельные стадии, одна база\]

После загрузки три стадии работают независимо, затем объединение пишет события в базу. Правки пользователя попадают в журнал и сразу видны агенту; проверенные метки идут в оценку качества.

**Стек.** Python; `yt-dlp` и FFmpeg; TensorFlow для извлечения признаков ветки A и PyTorch для моделей; `faster-whisper`; OCR с казахским языком или vision-модель для плашек; SQLite в режиме WAL; Streamlit с небольшим компонентом на YouTube IFrame API: встроенный плеер Streamlit не отдаёт текущее время, а оно нужно для кнопки «добавить событие здесь».

**Стадии как команды.** Каждая стадия запускается отдельной командой, пропускает уже готовое и пишет файл со своим форматом в каталог матча; Claude Code может писать и тестировать их независимо, а автор проверяет результат каждой стадии глазами.

| Файл в каталоге матча | Содержимое | Кто пишет |
| --- | --- | --- |
| `src.mp4`, `audio.wav` | видео до 720p, аудио 16 кГц моно | загрузка |
| `scoreboard.json` | счёт и игровое время по секундам, соответствие `t_v` → минута | табло |
| `plates.json` | найденные плашки: тип, время, команда, игроки, текст | плашки |
| `features.npy`, `scores.npy` | признаки кадров на 2 fps и оценки классов по времени | признаки и модель |
| `transcript.json` | реплики с языком, словами и временем | речь |
| `candidates.json` | кандидаты после NMS и итоговые события | объединение |

**База.** Таблицы `predictions` (неизменяемые предсказания), `edits` (журнал правок: add, move, retype, delete, verify), `transcript`, `players`; текущее состояние — представление `events_current` («предсказания последнего запуска плюс действующие (не отменённые) правки»). Журнал даёт откат правки, аудит «что предсказала модель и что исправил человек» и готовую разметку для оценки. SQLite выбран вместо JSON, потому что Streamlit перезапускает скрипт на каждое действие, а агент читает параллельно: транзакции избавляют от ручных блокировок.

**Фоновая обработка.** Streamlit запускает обработку отдельным процессом и каждые пару секунд читает файл статуса со стадией; очередей и воркеров нет. Для демо один матч обработан заранее, а в README указано, сколько занимает новая ссылка.

**Где что живёт.** Плееру достаточно YouTube, а экспорту клипа и кадрам для агента нужен скачанный файл, поэтому интерфейс и видео живут на одной машине. Если считать на сервере, маленькие результирующие файлы копируются на ноутбук, а видео скачивается на нём отдельно.

## 10. Стоимость и ресурсы

Бюджет на API — около 10 долларов на весь спринт; это план автора, а не измерение, и цифры ниже грубые прикидки до первого замера.

| Статья | Оценка | Как измеряем |
| --- | --- | --- |
| Вопрос к агенту | вход 10–25 тыс. токенов, выход около 1 тыс. | журнал токенов на каждый запрос |
| Описание по кадрам | плюс 6–8 тыс. входных токенов на 4–6 кадров | то же |
| Всего за спринт | порядка 200 запросов на разработку, оценку и демо | сумма журнала; лимит расходов выставляется в кабинете провайдера |
| Обработка матча (CV, OCR, Whisper, эмбеддинги) | локально, в API не тратится; десятки минут на матч, зависит от видеокарты | время каждой стадии пишется в журнал |
| Claude Code | отдельная статья, в 10 долларов не входит | не считается |

**Как не выйти за бюджет.** Разработка на дешёвой модели, сильная модель только для финальной оценки и демо; кэш ответов на повторные вопросы; лимит расходов у провайдера. Цены моделей проверяются на странице провайдера перед стартом.

**Для отчёта о стоимости.** Себестоимость обработки одного матча (GPU-время плюс токены) сравнивается с часами работы аналитика на ручной поиск; время стадий и токены берутся из журнала.

**Железо.** Собственный компьютер и сервер с видеокартой; модель карты и ограничение по времени сессий уточняются (команда `nvidia-smi`). Непрерывно 5 и более часов видеокарта недоступна, поэтому каждая стадия кэширует результат на диск и умеет продолжать с места остановки; обучение сквозных моделей с нуля не планируется.

## 11. План на 14 дней

План строится так, чтобы первая цифра появилась в начале: код метрик пишется первым, эталон размечается в дни 1–2.

&#91;embedded content: план на 14 дней · 7 этапов, одна развилка\]

В дни 3–4 обе ветки запускаются на 1-м тайме; к концу 4-го дня остаётся та, у которой лучше мягкая метрика, вторую не дорабатываем.

**Порядок отрезания при нехватке времени:**

1. описание эпизода по кадрам;
2. ветка B (T-DEED);
3. мини-стекер, остаются правила;
4. казахский лексикон для речи (казахский в вопросах и ответах агента остаётся).

Ядро, которое не режется: плашки и табло, ветка A, эталон и метрики, агент по событиям и транскрипту, интерфейс с исправлением и экспортом.

**Две практические вещи:**

- людей для эксперимента по времени нужно найти в первые дни и договориться на дни 13–14: иначе будет упор в чужое расписание;
- решения проекта (формат плашек, определения событий, окна) записываются в файл `CLAUDE.md` в репозитории, иначе Claude Code будет каждый раз придумывать их заново.

## 12. Риски и ограничения

Главный риск — перенос модели SoccerNet на КПЛ, потому что она обучена на европейских лигах; остальные риски связаны с малым объёмом данных и сроком.

| Риск | Что делаем |
| --- | --- |
| Модель SoccerNet хуже работает на КПЛ (другие планы камеры, графика, качество картинки) | гибрид с плашками и табло; две ветки с выбором к концу 4-го дня; в отчёте две цифры — SoccerNet и KFF |
| Один матч: метрики по редким классам статистически шаткие | подбор на 1-м тайме, тест на 2-м; доверительные интервалы; результат называется пилотом |
| Шаблоны плашек привязаны к графике KFF и могут отличаться на другом матче | проверить на втором матче, если он появится; в README описать, что подстроено под графику |
| Плашка выходит позже события | окна поиска по классам; задержки измеряются при разметке |
| Казахский ASR слабее русского; речь комментаторов иногда перекрывается | сначала проверка на 5 минутах; основная опора на плашки и CV; потерю перекрытой речи указать |
| Эксперимент по времени: 2 человека, склонность не замечать пропусков | порядок таймов меняется, сравниваются итоговые Precision и Recall, не только время |
| Сравнение с Gemini нельзя повторить пакетно | один заранее записанный запрос; ограничение указано |
| Права на видео | только разрешённые трансляции, видео и клипы не публикуются |
| Лицензия T-DEED GPL-3.0 | указать в отчёте; код ветки B изолирован |
| Сроки: 2 недели, один исполнитель | порядок отрезания в разделе 11; код метрик пишется первым |
| Описание по кадрам может содержать выдуманные детали | пометка «не проверено»; вырезается первым |
